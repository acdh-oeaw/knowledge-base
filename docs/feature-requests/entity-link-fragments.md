# Fragments (and search params?) on entity links

Status: investigated, not started (2026-11-09). Came up while finishing `data:clean:richtext-links`
(`packages/database/lib/richtext-link-cleanup-service.ts`).

## Motivation

The old clariah.at page `/funding-opportunities-for-junior-researcher/` was not imported as a page
of its own: its content is now the "Early Career" section of the "Förderung" page (entity
`01a16042-30f0-70be-9aa4-de6f5eb7a860`, slugs `funding` / `foerderung`). Exact targets would be:

- en: `/en/pages/funding#early-career-scholarships`
- de: `/de/pages/foerderung#early-career-foerderungen`

An entity link stores only `targetKind: "entity"` + `entityId`, so it cannot express the section.
The cleanup therefore maps those links to the Förderung page itself (see the comment on
`pages/funding-opportunities-for-junior-researcher` in
`packages/database/lib/legacy-clariah-at-paths.ts`). The links that should get the fragment once it
is supported are listed [below](#links-to-point-at-the-early-career-section).

## Current state

- Rich text is stored as tiptap JSON, so a new link attribute needs no database migration.
- A link mark (or `buttonLink` node) either has a plain `href`, or a reference: `targetKind` plus
  `assetKey` / `entityId` and no `href` (`packages/database/lib/link-targets.ts`).
- Read paths resolve entity references in one place, `annotateEntityLinkTargets`
  (`packages/database/lib/link-targets.ts`), which writes the resolved, locale-less `href` (plus an
  `entity` attribute with `href`, `label`, `type`, `locale`) onto the outgoing copy. Callers:
  - api: `annotateEntityLinks` in `apps/api/src/lib/content-blocks.ts` (resolves in the locale of
    the linking entity version, falling back to the default locale)
  - dashboard: `apps/knowledge-base/lib/content-blocks-service.ts` (labels only, no href)
- The OpenAPI schema does not describe rich-text attributes, so adding a `#fragment` to the
  resolved `href` does not change the documented api contract.
- Heading ids/anchors are not generated in this repo: the website (separate repo,
  github.com/acdh-oeaw/clariah-at-platform) derives them from the heading text
  (`Early Career Scholarships` → `#early-career-scholarships`).
- The link cleanup currently refuses to rewrite to an entity link when the old url has a query or
  fragment (review reason `legacy_clariah_at_entity_with_query_or_hash`); tracking params (`ref`)
  are dropped first. Path rewrites (home, listings, imprint) keep query and fragment.

## Proposed change (free-text fragment)

1. **Attribute**: add e.g. `fragment` (default `null`) to the link mark and the `buttonLink` node in
   `packages/ui/lib/rich-text-editor.tsx` (attribute definitions incl. `data-*` parse/render
   rules). Add it to every place that spells out all target attributes so retargeting clears it:
   `linkTarget` in the editor, `applyReplacement` in the link cleanup service.
2. **Read path**: in `annotateEntityLinkTargets`, append `#${fragment}` to the resolved `href` (and
   to `entity.href`?). Tests in `link-targets.test.ts`, and api tests.
3. **Editor UI**: optional "section anchor" input in the entity-link popover, shown in the link
   target summary. Largest part, but a single field.
4. **Link cleanup**: rich-text blocks belong to one locale version, so a per-locale fragment can be
   stored on each link. Extend `LegacyClariahAtEntity` with e.g. `fragments?: { de?: string; en?:
string }`, select the block's locale in `computeCleanups`, and pick the fragment by it.
   Also decide whether old urls _with_ a fragment may then become entity links carrying it instead
   of going to review (the old site's anchors will not match the new ones, so probably not).

Estimate: about a day including tests.

## Open questions

- **Search params**: allow a query string on entity links as well (e.g. a listing with a preset
  filter)? Same mechanics as the fragment (stored attribute, appended at read time), but query
  params are interpreted by the target page, so they are more of an api contract than a fragment
  is. Possibly one attribute (`suffix`/`urlSuffix`) vs. two (`fragment`, `searchParams`).
- **Website**: does it render `attrs.href` (then fragments just work) or build urls from
  `attrs.entity`? Not verified, needs a look at clariah-at-platform.
- **Silent breakage**: renaming a heading changes its website-generated id and breaks the fragment
  without anything here noticing (the page still loads, the browser just doesn't scroll).
- **Locale fallback**: when the target has no version in the linking locale, the api falls back to
  the default locale, where a stored fragment will usually not exist (harmless, same as above).
- **Heading picker** (later, if needed): let editors pick from the target's headings, with ids
  generated by the api and used by the website. Needs changes in both repos.
